RESTとは？

リソース指向で設計するAPI原則
RESTでは
  • URLはリソース（名詞）
  • HTTPメソッドで操作
  • ステートレス
  • 統一された構造

REST原則

① リソース指向
URLは名詞で設計
/users /users/1
② HTTPメソッドで操作
GET /users POST /users DELETE /users/1
③ ステートレス
毎回リクエストに必要情報を含める
Authorization: Bearer token
④ 統一インターフェース
/users /orders /products

RESTの例 / RESTでない例

REST
GET /users
DELETE /users/1
RESTでない
GET /getUsers
POST /deleteUser

REST APIとは

REST原則に従って設計されたAPI
GET /users GET /users/1 POST /users PATCH /users/1 DELETE /users/1

メリット

  • 設計が統一される
  • フロントとバックエンド分離しやすい
例：フロントとバック分離
GET /users return [ { id:1, name:"A" }, { id:2, name:"B" } ]
同じAPIを
  • Web
  • スマホ
  • バッチ
から利用できる
例：設計統一
GET /users GET /orders GET /products
パターンが統一される

デメリット

  • 複雑な取得に弱い
  • 複数API呼び出しが必要になる
例：複雑取得
GET /users/1 GET /users/1/orders GET /users/1/profile
複数回呼び出しが必要
専用APIを作る必要がある
GET /user-detail/1
複雑な取得用にAPIを追加するケースがある

ユースケース

  • 複雑な取得に弱い
  • オーバーフェッチが発生
  • API呼び出し増える

ユースケース

REST向き
  • CRUD中心システム
  • Webアプリ
  • スマホAPI
  • マイクロサービス
REST不向き
  • 複雑クエリ（GraphQL）
  • リアルタイム通信
  • ストリーミング

まとめ

API = 窓口 REST = 設計原則 REST API = RESTに従ったAPI
